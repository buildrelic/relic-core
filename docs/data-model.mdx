Relic has three type layers, each with a distinct job. Conflating them is the
mistake the split prevents.

1. **The rich ontology** (`ontology/`) is the typed source of truth for the
   domain: nested models, audit records, canonical URLs.
2. **The relational engram schema** (`engram/store.py`) is what Postgres holds:
   memory rows, people, and the joins between them.
3. **SkillIR** (`ontology/skill_ir.py`) is the contract for a compiled skill,
   ported verbatim from the system-design doc.

A fourth shape sits between ingestion and the store: the **episode body**, a
typed JSON contract in `relic.contracts.episode_body`. The mapping from each
body onto its row's derived columns is one pure function per artifact type in
[`relic.engram.derive`](https://github.com/buildrelic/relic-core/blob/main/packages/relic-engram/src/relic/engram/derive.py),
checked by `tests/test_derive.py`, so a body field the store depends on cannot
silently stop resolving.

## Why separate layers

The rich ontology is built for the typed API: it nests (`Person` has a
`ContactInfo`, an `AuditInfo`, a list of `Link`) and carries audit metadata.
The store needs none of that on the row: it needs identity, a search surface,
and the body itself. So the row keeps the typed body verbatim in `jsonb` and
derives flat columns from it, and the rich models stay the source of truth for
the typed domain.

## Layer 1: the rich ontology

Lives in `ontology/`, ported from the Relic system-design doc. Every entity is a
node; relationships are expressed as `Id` reference fields rather than nested
objects, and enums are lowercase `Literal` aliases.

### Primitives

[`primitives.py`](https://github.com/buildrelic/relic-core/blob/main/packages/relic-core/src/relic/ontology/primitives.py) holds the shared building
blocks: `Id` (a `str` alias), `TimePoint` (a `datetime` alias), `TimeRange`,
`Money`, `Link`, `ContactInfo`, `AuditInfo`, `TextBlob`, and `Taggable`.
`AuditInfo` (created_by, created_at, last_edited_by, last_edited_at) is the
provenance record carried by most entities.

### Engineering subset

[`entities.py`](https://github.com/buildrelic/relic-core/blob/main/packages/relic-core/src/relic/ontology/entities.py) holds the types the prototype
actually ingests:

- `Person`: a teammate or external collaborator (extends `Taggable`, carries
  `ContactInfo`, `profiles`, `external_org`, `audit`).
- `Repo`, `PullRequest`, `Review`, `Issue`: the GitHub and Linear shapes. Each
  carries a canonical `url` for provenance and an `audit` record.
- `Procedure` plus `ProcedureEvidence`: an inferred standard procedure with
  `confidence` (0 to 1), `support` (a count), and a list of evidence, the target
  output of the Phase 4 detector.

`Person` and the primitives are ported from the doc. `Repo`, `PullRequest`,
`Review`, `Issue`, and `Procedure` were designed here to fit Phase 2 ingestion.

### Broader org model

[`org.py`](https://github.com/buildrelic/relic-core/blob/main/packages/relic-core/src/relic/ontology/org.py) ports the rest of the system-design
ontology, beyond what the prototype ingests today: `Employee` (extends `Person`),
`Team`, `Customer`, `Product`, `Project`, `Document`, `Meeting`, `Decision`,
`Policy`, and the OKR types (`OKRGoal`, `KeyResult`, `Metric`). These are defined
and exported but not yet populated by any connector. They are the schema the
platform grows into as more sources land.

All ontology types are re-exported from
[`ontology/__init__.py`](https://github.com/buildrelic/relic-core/blob/main/packages/relic-core/src/relic/ontology/__init__.py).

## Layer 2: the relational engram schema

[`store.py`](https://github.com/buildrelic/relic-core/blob/main/packages/relic-engram/src/relic/engram/store.py)
owns the DDL (the `_SCHEMA` constant), applied idempotently by
`ensure_schema()`. Five tables, plus one reserved:

| Table | Key | What it holds |
|---|---|---|
| `workspaces` | `id` (text) | One row per tenant: the web app's Clerk scope, or `RELIC_WORKSPACE` locally |
| `people` | `id` (uuid) | display_name, github_login, linear_id, slack_id, email, per workspace |
| `memories` | `id` (uuid), `UNIQUE (workspace_id, name)` | One row per artifact: scope, source, artifact_type, title, url, reference_time, the `jsonb` body, content_hash, schema_version, search_text, the generated `search_tsv`, user_edited/edited_by/edited_at, document_id |
| `memory_people` | `(memory_id, person_id, role)` | Roles: author, reviewer, requested_reviewer, assignee, participant |
| `memory_paths` | `(memory_id, path)` | File paths a memory touches |
| `memory_embeddings` | reserved | The pgvector fast-follow, commented in the DDL, not built |

Two schema decisions worth knowing:

- **Person identity is a precedence, enforced by partial unique indexes.** A
  person keys on `github_login`, else `email`, else `display_name`. Partial
  indexes because Postgres treats NULLs as distinct: a plain
  `UNIQUE (workspace_id, github_login)` would let NULL-login duplicates through.
- **`search_tsv` is generated.** A stored tsvector over `title` plus
  `search_text`, GIN-indexed, so search stays consistent with the columns by
  construction.

The mapping from each artifact type's body onto the derived columns (title,
url, search_text, markdown, people, paths) is
[`derive.py`](https://github.com/buildrelic/relic-core/blob/main/packages/relic-engram/src/relic/engram/derive.py):
deterministic, pure, and degrading (a malformed body lands as a raw-text row,
never a failed episode). See [Memory and recall](/memory-and-recall) for the
full walk.

## The episode body (a typed, versioned contract)

The bridge from ingestion to the store. [`mappers.py`](https://github.com/buildrelic/relic-core/blob/main/packages/relic-ingest/src/relic/ingest/mappers.py)
turns each fetched record into an `EpisodeSpec`. The `body` is a JSON string on
the wire, built from a typed Pydantic model in
[`relic.contracts.episode_body`](https://github.com/buildrelic/relic-core/blob/main/packages/relic-core/src/relic/contracts/episode_body.py)
(`PrEpisodeBody`, `IssueEpisodeBody`, `DocEpisodeBody`,
`ConversationEpisodeBody`, `AgentSessionEpisodeBody`) and serialized with
`model_dump_json()`. The model is the shared schema both sides read: ingest
builds it, and the engram side (`derive`, and later the detector and compiler)
validates it against the same type, so the seam cannot drift. Dispatch keys on
the `source_type` discriminator.

A PR episode body (`schema_version` 2):

```json
{
  "schema_version": 2,
  "source_type": "pull_request",
  "context": "merged PR, 2 reviews, 1 file",
  "repo": {"full_name": "buildrelic/relic-core", "url": "...", "default_branch": "main"},
  "pull_request": {
    "number": 12, "title": "...", "description": "...",
    "url": "https://github.com/buildrelic/relic-core/pull/12",
    "state": "merged", "created_at": "...", "merged_at": "...",
    "base_ref": "main", "head_ref": "paris/auth-routing",
    "labels": ["area:auth", "type:fix"],
    "author": {"login": "...", "profile_url": "..."},
    "co_authors": [{"name": "...", "email": "..."}],
    "timestamps": {"created_at": "...", "first_review_at": "...", "approved_at": "...", "merged_at": "...", "time_to_merge_hours": 26.0},
    "diff_stats": {"total_additions": 80, "total_deletions": 10, "changed_files": 1}
  },
  "reviews": [{"reviewer": {"login": "...", "profile_url": "..."}, "state": "APPROVED", "submitted_at": "...", "url": "...", "comment": "..."}],
  "requested_reviewers": [{"name": "alice", "kind": "user", "profile_url": "..."}, {"name": "auth-team", "kind": "team"}],
  "files": [{"path": "src/auth/login.py", "additions": 80, "deletions": 10}],
  "commits": [{"sha": "...", "message": "...", "author_login": "..."}],
  "checks": [],
  "linked_issues": [{"identifier": "buildrelic/relic-core#100", "relation": "closes"}]
}
```

An issue episode body is an `issue` object with identifier, title, description,
state, url, assignees, labels, parent, and created/closed times. The same shape
covers GitHub and Linear, since both map to the `IssueRec` record. Reserved fields
default empty in the contract so the schema is the full target while capture fills
it wave by wave: `checks` on the PR body, and on the issue the `priority`,
`estimate`, `cycle`, `state_history`, and `relations` Linear has but GitHub does
not. The doc, conversation, and agent-session bodies carry the shapes their
sources produce: a Notion page's title, url, authors, and text; a Granola
meeting's participants, summary, decisions, and transcript; a Claude Code
session's actor, cwd, files touched, summary, and distilled transcript.

Each `EpisodeSpec` also carries a `name` (for example `PR buildrelic/relic-core#12`),
a `source_description`, a `reference_time` (the merge or creation timestamp, parsed
tz-aware), the `group_id` (the scope slug), and the `schema_version`.

<Warning>
**Two invariants the body shape must keep.**

- **Citation anchors.** `pull_request.url` / `issue.url` (and each body's `url`
  field) are read by
  [`derive.py`](https://github.com/buildrelic/relic-core/blob/main/packages/relic-engram/src/relic/engram/derive.py)
  into the row's `url` column, which every recalled fact cites. Moving them
  degrades every citation.
- **The name is the identity.** `schema_version` and every new field live in the
  body, never in `name`. The checkpoint dedups on `name` and the store upserts on
  `(workspace_id, name)`, so a version woven into the name would re-land every
  episode as a new row instead of refreshing it in place.
</Warning>

The free-text fields are clipped (description 2000 chars, review comment 1500, commit
message 1000) and the assembled body is trimmed to a per-episode budget
(`_fit_budget`), so a pathological artifact cannot bloat its row. Bot reviews are
dropped and human reviews capped, most-informative kept
([`_clip`](https://github.com/buildrelic/relic-core/blob/main/packages/relic-ingest/src/relic/ingest/mappers.py), `_select_reviews`).

<Note>
Several body fields are richer than what `derive` surfaces into the search
columns today (per-file `additions`/`deletions`, `co_authors`, derived
`timestamps`, `linked_issues` relations). The body keeps them verbatim in
`memories.body`, so the detector and compiler (Phase 4) can read them without a
re-ingest. Capture leads, consumption follows.
</Note>

<Warning>
**Raw payload shapes are not uniform.** The episode body above is stable, but the
verbatim source payloads under `data/raw/` are not. PRs are fetched over GraphQL,
so their raw payload is the **camelCase GraphQL node** (`createdAt`, `mergedAt`,
`author { login }`); issues still come over REST, so theirs is the **snake_case REST**
body (`created_at`, `html_url`), as are PRs from any pre-GraphQL ingest. A future pass
that re-maps from `data/raw/` must branch on shape (or on `source`) rather than assume
one casing.
</Warning>

## Layer 3: SkillIR

[`skill_ir.py`](https://github.com/buildrelic/relic-core/blob/main/packages/relic-core/src/relic/ontology/skill_ir.py) is the contract for a compiled
skill. It is ported verbatim from the system-design doc and must not drift,
because the same schema becomes the MCP tool contract and the rendered
`SKILL.md`.

```
SkillIR
├── skill_id, semver                 # identity + versioning
├── title, description               # human-facing (description is the routing rule)
├── scope                            # org | team | repo | project | person
├── inputs:  dict[str, FieldSpec]    # typed contract, also the MCP input schema
├── outputs: dict[str, FieldSpec]
├── preconditions: list[str]         # execution guardrails
├── safety_checks: list[str]
├── citations: list[Citation]        # grounding: label, url, source_type
├── status                           # draft | verified | deprecated
├── owner
├── last_verified_at
└── tags: list[str]
```

`FieldSpec` is a single typed field (type, description, required, default).
`Citation` is a grounded source (label, url, and a `source_type` of pr, issue,
comment, doc, or message). An example lives at
[`examples/skills/pr-review-routing.json`](https://github.com/buildrelic/relic-core/blob/main/examples/skills/pr-review-routing.json).

How `SkillIR` is stored, rendered, served, and emitted is covered in
[Skills](/skills).
