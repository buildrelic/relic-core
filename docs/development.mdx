Relic is a uv workspace on Python 3.12: five packages under `packages/` (see
[Architecture](/architecture)), installed editable into one shared venv. The
toolchain is ruff (lint and format), pyright (types), pytest (tests), and
import-linter (subsystem boundaries). CI runs all four, with ruff in check-only mode: `ruff format` is local, via `just fmt`.

## Requirements

- Python 3.12 (`.python-version` pins it)
- [uv](https://docs.astral.sh/uv/)
- [just](https://github.com/casey/just) (task runner)
- Docker (for Postgres, the engram store)
- `gh` CLI logged in, or a `GITHUB_TOKEN`

No model API key is needed for development: ingest, recall, and the whole test
suite run without one.

## Setup

<Note>
  New contributors should start with the [Quickstart](/quickstart), which walks
  setup plus your first ingest and recall. This page covers the contributor
  workflow: setup, tests, CI, and conventions.
</Note>

From a fresh clone:

```bash
just setup
```

`just setup` installs Python 3.12 with uv, syncs the dev dependencies, creates
`.env` from `.env.example` if you do not have one, starts Postgres and waits for
it to report healthy, installs the pre-commit hook, then runs `relic doctor`. It
is safe to re-run. The engram schema is applied automatically on first use.

Missing keys show as missing in the doctor report. Fill them into `.env`, then run
`just doctor` again. Run `just` with no arguments to list every recipe.

## Daily commands

```bash
just                          # list every recipe
just doctor                   # is the environment wired up?
just check                    # lint, types, tests (what CI runs)
just fmt                      # format with ruff
just up                       # start Postgres, wait for healthy
just down                     # stop Postgres, keep the volume
just loop-smoke               # the e2e closed-loop smoke, against a real Postgres
just serve                    # MCP server over stdio, for manual testing
just ingest astral-sh/uv 20   # ingest a repo, capped at 20
just recall "who reviews auth changes?"
```

`just check` runs ruff, pyright, pytest, and lint-imports, the same four CI runs.
`just lint`, `just types`, `just test`, and `just imports` run them one at a time.
`just test` excludes the `e2e` marker; run that deliberately with
`just loop-smoke`. `just reset-db` and `just clean` are destructive: the first
wipes the Postgres volume (every workspace's memories), the second removes local
state under `data/` and keeps the volume.

`just check` runs pyright and pytest as `uv run python -m ...` so they work
regardless of the installed entry-point shebangs.

## Conventions

Tooling config is in [`pyproject.toml`](https://github.com/buildrelic/relic-core/blob/main/pyproject.toml).

- **ruff.** Line length 100, target py312, lint rules `E`, `F`, `I`, `UP`, `B`,
  `SIM`. One per-file ignore: `skill_ir.py` keeps `Optional[...]` (`UP` off)
  because it is ported verbatim and must not drift from the system-design doc.
- **pyright.** Basic mode over `packages` and `tests`, against the `.venv`.
- **pytest.** `asyncio_mode = "auto"` (async tests need no decorator), quiet
  output, tests under `tests/`. One marker: `e2e`, the full-loop smoke, excluded
  from `just test` and run via `just loop-smoke`.

The house voice for all prose (docs, UI, errors, commit messages) is in
[`AGENTS.md`](https://github.com/buildrelic/relic-core/blob/main/AGENTS.md). The short version: short declarative sentences, no em
dashes, specifics over adjectives, real names only, lowercase product terms
(memory, capture, recall).

## Branches, commits, and PRs

We track work in Linear. From [`AGENTS.md`](https://github.com/buildrelic/relic-core/blob/main/AGENTS.md):

- **Branches.** Work on an issue from the branch Linear generates for it, used as
  is, for example `paris/rel-10-ingest-run-observability`.
- **Commit titles.** Short and skimmable, read like a person dashed them off, no
  `feat:`/`fix:` prefixes, no emoji. When the commit relates to a Linear issue,
  append `[part of <issue-ID>]`, for example `... [part of REL-10]`.
- **Commit descriptions.** Carry the detail: what changed and why, context,
  tradeoffs. Write the reasoning the diff cannot show.
- **PR bodies.** A walkthrough, not a one-liner: every change, its consequences,
  and how to test it.

## CI

[`.github/workflows/ci.yml`](https://github.com/buildrelic/relic-core/blob/main/.github/workflows/ci.yml) runs on push to `main`
and on every PR. It spins up a `postgres:16` service container, syncs the whole
workspace with `uv`, then runs ruff (`ruff check`, lint only), pyright, lint-imports, and pytest in sequence, with `DATABASE_URL` set on the pytest step so
the Postgres-gated store tests always run. CI does not verify formatting; run `just fmt` locally. A red check on any of the four fails the build. `just check` runs the
same four locally before you push.

## Documentation

`docs/` is the canonical documentation for the codebase and the platform, built
with Mintlify. Treat it as the source of truth and keep it in sync with your
change: a PR or commit that changes behavior, a contract, a command, config, the
data model, or a process updates the affected page under `docs/` in the same
change. Docs and code ship together. The full rule and the change-to-page map are
in [`AGENTS.md`](https://github.com/buildrelic/relic-core/blob/main/AGENTS.md).

Pages are `.mdx` with `title` and `description` frontmatter, and the navigation
lives in `docs.json`. Preview locally with `mint dev` from `docs/`, and check the
build with `mint validate` (the Mintlify CLI needs an LTS Node).
