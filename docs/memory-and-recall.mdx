Memory is the **engram store**: relational rows in Postgres plus an optional
document mirror in Firestore. Every ingested artifact (a PR, an issue, a meeting,
a Notion page, an agent session) is one row in `memories`, joined to the people
and file paths it names. Recall is Postgres full-text search over those rows, and
every recalled fact carries the memory it came from.

There is no LLM anywhere in this path. Ingest lands typed episodes as rows
deterministically, and recall ranks them with `ts_rank_cd`. The pivot from the
Graphiti/FalkorDB knowledge graph is recorded in
[ADR-0007](/adr/0007-engram-store-pivot).

## The store

[`store.py`](https://github.com/buildrelic/relic-core/blob/main/packages/relic-engram/src/relic/engram/store.py)
holds the one adapter, `EngramStore`. It owns every SQL statement and the
document mirror; the rest of the platform depends on two Protocols
(`EngramReader` for search, `EngramWriter` for `add_episode` and
`ensure_schema`) and plain value types, never on asyncpg. The seam discipline
from the graph era (ADR-0003) carried over to the store that replaced it.

`open_engram(settings)` connects a pool to `DATABASE_URL`, applies the schema,
wires the Firestore mirror when configured, and binds the store to
`RELIC_WORKSPACE`. `postgres_reachable(dsn)` is the fast TCP probe the CLI runs
before an ingest.

## The schema

Postgres is authoritative. relic-core owns the DDL (the `_SCHEMA` constant in
`store.py`), applied by an idempotent `ensure_schema()` on every store open, so
the URL is the only coordinate a deploy needs. The landing web app reads and
edits against the same tables, so a schema change here is a cross-repo contract
change.

| Table | What it holds |
|---|---|
| `workspaces` | One row per tenant. The id is the web app's Clerk scope (`orgId ?? userId`), or `RELIC_WORKSPACE` (default `local`) for the CLI and daemon. |
| `people` | Humans named by memories, per workspace: `display_name`, `github_login`, `linear_id`, `slack_id`, `email`. |
| `memories` | One row per artifact. Identity, the typed episode body, the search columns, and the edit flags (below). |
| `memory_people` | Person-to-memory joins with a `role`: `author`, `reviewer`, `requested_reviewer`, `assignee`, or `participant`. |
| `memory_paths` | File paths a memory touches, one row per path, indexed for prefix matching. |

The `memories` row carries:

- **Identity.** `workspace_id`, `scope` (the former `group_id` slug, the
  per-source partition within a workspace), `source`, `artifact_type`, `name`
  (the episode name, e.g. `PR owner/name#42`), and `UNIQUE (workspace_id, name)`.
- **The body.** The typed episode JSON in a `jsonb` column, plus `content_hash`
  and `schema_version`.
- **Search.** `title`, `url`, `search_text`, and a generated `search_tsv`
  tsvector over title plus search text, GIN-indexed.
- **Edits.** `user_edited`, `edited_by`, `edited_at`: set when a human edits the
  memory in the web workspace.
- **The mirror.** `document_id`, the Firestore document this row mirrors to,
  NULL when the mirror is off.

Person identity resolves by precedence: `github_login`, else `email`, else
`display_name`. The uniqueness is enforced by partial unique indexes rather than
one plain constraint, because Postgres treats NULLs as distinct and a plain
`UNIQUE (workspace_id, github_login)` would let NULL-login duplicates through.
A ref with none of the three (a ghost account) gets no row and no join.

A `memory_embeddings` pgvector table is **reserved** in the DDL as a comment,
not built. It is the fast-follow if full-text search falls short on the
scorecard.

## Derive: from episode body to row

[`derive.py`](https://github.com/buildrelic/relic-core/blob/main/packages/relic-engram/src/relic/engram/derive.py)
is pure, no I/O. One function per artifact type turns the typed episode body
(`PrEpisodeBody`, `IssueEpisodeBody`, `DocEpisodeBody`,
`ConversationEpisodeBody`, `AgentSessionEpisodeBody`) into what the store
writes:

- **`title` and `url`.** The row's display name and citation anchor.
- **`search_text`.** The text that feeds full-text search: titles,
  descriptions, labels, reviewer logins, commit messages, and file paths (both
  whole and split on `/`, so a query like "auth" matches `src/auth/token.py`).
- **`markdown`.** The rendered document the web workspace displays and lets a
  human edit.
- **`people` and `paths`.** The `(person, role)` pairs for `memory_people` and
  the file paths for `memory_paths`.

Dispatch keys on the body's `source_type` discriminator. An unknown or
malformed body degrades to a raw-text row rather than failing the episode.
`derive.py` lives in the engram package, not ingest: both sides share the body
models through `relic.contracts.episode_body`, and the import contract forbids
engram from importing ingest.

## Supersession is the upsert

`add_episode` upserts on `(workspace_id, name)`. A re-presented episode with
changed bytes replaces its row in place; an identical replay is a no-op
refresh. There is no removal cascade and no way to fork: the name is the
identity, so one artifact is always exactly one row.

## User edits win

A human edit in the web workspace sets `user_edited` (with `edited_by` and
`edited_at`). From then on, a re-ingest of the same artifact refreshes the
structured columns (`body`, `content_hash`, `url`, `reference_time`) but never
the human's `title` or `search_text`, and skips the Firestore mirror for that
row so the edited markdown is never clobbered. `--fresh` clears the checkpoint
but still respects the edit.

## Workspace and scope

Every row carries a `workspace_id` and every read binds to one, so an unscoped
read is workspace-wide, never tenant-wide. Within a workspace, `scope` is the
per-source partition: a repo slug like `buildrelic__relic-core`, a Granola
owner like `granola__paris@buildrelic.com`, or a Notion workspace like
`notion__buildrelic`. Recall, `query`, and `eval` narrow to one scope with
`--repo` (or `TARGET_REPO`); without one they search the whole workspace.

The web app writes with its Clerk scope as the workspace; the CLI and daemon
write to `RELIC_WORKSPACE` (default `local`). The Zone machinery from
[ADR-0005](/adr/0005-tenant-zone-access-model) and
[ADR-0006](/adr/0006-sound-graph-for-consumers) is retired with the graph; the
workspace column is the tenancy boundary now (ADR-0007).

## The Firestore mirror

[`documents.py`](https://github.com/buildrelic/relic-core/blob/main/packages/relic-engram/src/relic/engram/documents.py)
is the NoSQL half. Documents live at
`engram/{workspaceId}/documents/{documentId}` and carry `memoryName`, `scope`,
`source`, `artifactType`, the typed `body`, the rendered `markdown`, and
`updatedAt`. The `markdown` is what the landing web app's Drive-style Memory
workspace renders and lets a human edit.

The mirror is optional and best-effort. It is configured by
`FIREBASE_PROJECT_ID`, `FIREBASE_CLIENT_EMAIL`, and `FIREBASE_PRIVATE_KEY`, the
same service-account env names the landing app uses. Unconfigured, documents
stay local-only (`memories.body` in Postgres remains authoritative and
`document_id` stays NULL). The mirror write runs after the row's transaction
commits and never raises: a Firestore outage degrades the web UI, never an
ingest. User-edited rows are skipped entirely.

## Recall: facts with sources

[`recall.py`](https://github.com/buildrelic/relic-core/blob/main/packages/relic-engram/src/relic/engram/recall.py)
is the general path and the keystone of the "every answer cites its source"
promise. The answer shapes and the rendered block are carried over verbatim from
the graph era: `format_answer`'s output is a seam (the daemon injects it onto
prompts, the MCP `recall_memory` tool returns it), so its format must not drift.

```
RecallAnswer
├── query: str
└── facts: list[RecalledFact]
        ├── fact: str           # "<title> — <snippet>"
        ├── relation: str       # the artifact type (pull_request, issue, ...)
        └── sources: list[Source]
                ├── label: str  # the memory name, e.g. "PR owner/name#12"
                └── url: str?   # the row's url column
```

The engine is Postgres full-text search, two passes:

1. **Websearch semantics first.** `websearch_to_tsquery('english', query)`
   against `search_tsv`, ranked by `ts_rank_cd` (ties broken by
   `reference_time`), with a query-focused snippet from `ts_headline`.
2. **An any-term fallback.** When the first pass finds nothing, the query's
   words are re-joined with `OR` and run again. Hook prompts are natural
   language ("who worked on the webhook receiver?"), and one word absent from
   the corpus must not blank the whole recall; `ts_rank_cd` still puts the rows
   matching the most terms first.

Each hit becomes one fact: the row's title, then the headline snippet, with the
memory's `name` as the source label and the row's `url` as the citation. Recall
never raises: if the store is unavailable it returns an empty answer.
`format_answer` renders the cited block, each fact on its own line, each source
indented beneath it.

## Query: people, one SQL statement

[`queries.py`](https://github.com/buildrelic/relic-core/blob/main/packages/relic-engram/src/relic/engram/queries.py)
backs `relic query`. `reviewers_of` answers the review-routing question ("who
reviews auth changes?") as one SQL query over the `memory_people` join, the
`memory_paths` table, and full-text search: people with a `reviewer`, `author`,
or `requested_reviewer` role on memories whose paths match the text (`ILIKE`)
or whose `search_tsv` matches it, weighted by how many memories support them.
It is deterministic where the old Cypher walk was best-effort, and like recall
it never raises: a store failure returns an empty list.

## Eval: the recall scorecard

[`scorecard.py`](https://github.com/buildrelic/relic-core/blob/main/packages/relic-engram/src/relic/scorecard.py)
measures recall quality as a small set of numbers. A gold set
([`eval/github_recall.json`](https://github.com/buildrelic/relic-core/blob/main/eval/github_recall.json))
names a repo and a list of cases, each a question plus the PR or issue numbers
whose content answers it.

`relic eval` runs recall for each question, then `score_case` walks the recalled
facts in ranked order and records which expected PR or issue URLs were cited and
how highly. A match is an exact URL comparison after case and trailing-slash
normalization (GitHub URLs are case-insensitive, and a cosmetic near-miss must
not score zero). From that, `summarize` reports three aggregates plus a
per-case line:

- **Hit rate.** Share of cases where at least one expected source was cited.
- **MRR.** Mean reciprocal rank of the first fact that cites an expected
  source. Rank is counted in facts, the unit recall orders, so this is the
  number to tune ranking against.
- **Coverage.** The mean share of each case's expected sources found, across
  all cases. One hit out of two expected PRs is half coverage, not a clean pass.

There is no LLM judge. Scoring is a deterministic URL comparison, so the ruler
costs nothing beyond the recall calls it measures. It is also the ruler for the
pivot's core trade: full-text search does not do semantic matching, and the
scorecard is what says whether that matters. `relic eval --json out.json`
additionally writes the run as JSON so metrics track across runs. `load_gold`
rejects gold sets that would score misleadingly.

## History: the graph era

Memory storage has moved twice. Embedded Kuzu was replaced by FalkorDB (Kuzu's
`group_id` partitioning crashed and its full-text search did not work), and the
Graphiti/FalkorDB temporal knowledge graph was then replaced by this store
([ADR-0007](/adr/0007-engram-store-pivot)): LLM extraction dominated ingest
wall clock at roughly 99.5 percent, and the product needed a memory a human can
see and correct. The recall seam (`RecallFn`, the `format_answer` block), the
episode contract, and every ingest mapper survived both moves unchanged. Git
history preserves the graph implementation.
