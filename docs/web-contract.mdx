This page is the handoff from the web app (Zidan, the landing repo) to relic-core's
HTTP API (`relic serve-http`). It pins what the web app calls and the exact shapes it
expects back. Two seams cross the repos: this HTTP API (the connector control
plane), and the engram store itself, which landing reads directly for its Memory
workspace. Read it before changing `relic serve-http`, the ingest trigger, or the
connector and ingest status endpoints.

The shapes here mirror `lib/relic/client.ts` in the landing repo, and the landing
repo carries its own copy of this contract (`relic-core-contract.md`). Those files
are the executable definition. If a shape here disagrees with the code, the code
wins and this page is stale.

## Ownership boundary

The web app owns Clerk identity and its own Firestore `orgs/*` collections:
connector config, per-user OAuth tokens, selected repos, ui state. relic-core
never reads `orgs/*`. When relic-core needs something the web app holds, the web
app passes it over this API.

relic-core owns the engram store schema (the Postgres tables and the Firestore
`engram/*` documents), ingest, recall, and this HTTP API. Landing reads the
engram store directly for `/app/memory` and writes back exactly one thing, a
human's document edit (see the engram store seam below).

Recall stays on MCP and the daemon. `relic serve` exposes a `recall_memory` tool
over MCP, and the `relic daemon` loopback surface does recall-on-inject plus
manual recall. Do not add a recall HTTP endpoint or a web recall surface. One
was built and removed (PR #28 closed). The web app is a connector control plane
plus the Memory workspace, not a recall ui.

## Auth and transport

The web app calls this API server-side, from code already behind its Clerk gate. The
base url is `RELIC_CORE_API_URL`. When `RELIC_HTTP_TOKEN` is set, the web app sends
`Authorization: Bearer <token>`, matching `relic serve-http --token`.

Per-user auth and per-workspace writes are landed: `POST /v1/ingest` ingests as
the connecting user's token and lands rows under the caller's workspace. What is
not landed is tenant-scoped recall; see the multi-tenancy section.

## Endpoints (built, keep stable)

### GET /v1/connectors

Per-source connection state and counts, synthesized from the on-disk ingest
checkpoints. No store needed. The web app calls this to overlay live status onto its
static connector catalog. Sources today: `github`, `linear`, `granola`, `notion`.

```json
{ "connectors": [
  {
    "source": "github",
    "connected": true,
    "itemCount": 84,
    "itemLabel": "commits",
    "lastSyncAt": "2026-06-24T01:00:00Z",
    "repos": ["buildrelic/relic-core"]
  }
]}
```

`lastSyncAt` is ISO 8601 or null. `source` is `github`, `linear`, and so on.

### GET /v1/ingest/runs

Run history plus rollup totals. Query params: `repo` (optional, filter to one
repo), `source` (optional, filter to a non-repo connector like `granola` or
`notion`, whose runs carry no repo), and `limit` (default 50). The web app fans
out one call per connected repo plus one per non-repo source and merges the
results.

```json
{
  "runs": [
    {
      "id": "r1",
      "repo": "buildrelic/relic-core",
      "source": "GitHub",
      "startedAt": "2026-06-24T00:54:00Z",
      "durationSeconds": 64,
      "attempted": 90,
      "loaded": 84,
      "skipped": 6,
      "failed": 0,
      "status": "success",
      "note": "optional human note"
    }
  ],
  "totals": { "memories": 14820, "sourcesConnected": 2, "lastRunAt": "2026-06-24T00:55:00Z" }
}
```

`status` is `success`, `running`, or `failed`. `startedAt` and `lastRunAt` are ISO or
null.

Totals are scoped to the filter: a `repo` call counts only that repo's
checkpoint ledger, a `source` call only that source's per-scope ledgers, and an
unfiltered call counts everything. So the web app's merge (summing per-partition
`totals.memories`, taking the max `lastRunAt`) does not overcount.

### GET /v1/status

Health and liveness. The web app uses it for the live-versus-mock decision.

### POST /v1/ingest

Trigger an ingest. The github webhook calls this on `pull_request.closed`
and `issues` events. The checkpoint makes the re-run incremental.

```json
{
  "source": "github (default) | granola | notion",
  "repo": "owner/name (required for github)",
  "token": "gho_... (optional)",
  "workspace": "org_2ab... (optional)"
}
```

`token` is the connecting user's secret for that source: a github oauth token, a
granola `grn_` key, or a notion integration token. When set, ingest
authenticates as that user and reads their data. When absent or blank, ingest
falls back to the server's own credentials for that source. The token lives in
the request body only: relic-core hands it to the ingest process through the
environment, never argv, and never logs, stores, or returns it. A malformed
token (whitespace, control bytes, over 255 chars) is rejected with 400 rather
than run as the wrong identity.

`workspace` is the engram workspace the run writes into (`workspaces.id`, the
web app's Clerk scope `orgId ?? userId`). Landing sends it whenever it knows the
scope: connect and sync actions, the GitHub connect callback, and the webhook
(looked up from Firestore by `installationId`). It is validated (up to 128
chars, printable, no whitespace, no leading `#`; a bad shape is a 400) and
forwarded to the spawned ingest as `RELIC_WORKSPACE`. Absent, the run lands
under relic-core's own `RELIC_WORKSPACE`.

Returns 202 when the run is accepted (spawns `relic ingest`), 409 when a run for
that scope is already in flight, and 400 for a non-JSON body, an unknown source,
a github body whose repo is not `owner/name`, a malformed token, or a malformed
workspace.

## REL-102: the per-user-token path (landed)

`POST /v1/ingest` accepts a per-user `token`, and both sides are done. The
design that shipped:

- **relic-core side.** The forwarded token overrides the server's credential for
  that one run. For github, the child process probes the user token before the
  heavy fetch and falls back to the server's `GITHUB_TOKEN` only on a definitive
  401 (an expired or revoked token is well-formed, so format validation cannot
  catch it). relic-core stays stateless on user secrets: environment, never
  argv, never logged or stored.
- **landing side.** The webhook has no Clerk session, so it looks up the
  connecting user's stored oauth token, and the Clerk scope it lives under, by
  `installationId`, and sends `{ repo, token, workspace }`. No token found means
  `{ repo }` only, which falls back to the server token.

Landing passes the token rather than relic-core minting one from
`installationId`: landing already holds it in Firestore, and it keeps relic-core
free of the github app private key.

## Multi-tenancy

For external teams, not our own org.

- **Workspace-scoped writes are landed.** Every memory row carries a
  `workspace_id`, the `workspace` field on `POST /v1/ingest` routes a run into
  the caller's workspace, and every store read binds to one workspace.
- **Tenant-scoped recall is not.** The MCP server and the daemon recall from the
  server's own `RELIC_WORKSPACE`; served recall does not yet carry a per-caller
  tenant scope.
- **A hosted, per-user-authed MCP endpoint.** External partners need something to
  point their agent at. Recall is local stdio today.

The last two are backend-owned and gate the real launch. The connector control
plane on the web side is done.

## The engram store seam

Beside this HTTP API, landing reads the engram store directly for `/app/memory`:
the Postgres tables for search and listing, and the Firestore documents at
`engram/{workspaceId}/documents/{documentId}` for content. relic-core owns the
schema (the `_SCHEMA` constant in
[`store.py`](https://github.com/buildrelic/relic-core/blob/main/packages/relic-engram/src/relic/engram/store.py));
landing codes against it in `lib/engram-store.ts`, so a DDL or document-shape
change here is a cross-repo contract change with the landing repo's
`relic-core-contract.md`.

Landing writes back exactly one thing: a human's document edit. The edit path
writes the Firestore `markdown` first, then the Postgres row (`search_text`,
`user_edited`, `edited_by`, `edited_at`), so a half-failed save loses search
freshness, never the user's text. Re-ingest respects the flag: an edited row
keeps its title and search text, and its Firestore document is never
overwritten. See [Memory and recall](/memory-and-recall).

## What the web app already handles

So relic-core does not duplicate it: the connect and auth ui, oauth flows and csrf,
token storage in Firestore, the github webhook receipt with hmac verification and
uninstall cleanup, the connectors, ingest, settings, and memory pages, and org
members and roles through Clerk. At the seam, relic-core's job is narrow. Serve
the four endpoints above with these shapes (per-user token and workspace on
`/v1/ingest` already wired), own the engram schema, and keep recall on MCP and
the daemon.
